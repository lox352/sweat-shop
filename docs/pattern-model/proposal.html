Patterns as instructions

A design is compiled once, in CI, into an immutable sequence of instructions. The site only interprets it. Progress is a place in that sequence, and a project always points at the exact version it started on. Below is how the sequence should be modelled so it stays extensible: kinds of operation with many variants each, and composite instructions built from atomic ones.

The recommendation in short

  1. Three layers, with the boundary in CI. Design source, which can be slow and clever, compiles to a written pattern: what a printed pattern says, round by round. That expands to an instruction stream: one entry per atomic action. Both are made in CI. The browser only reads the stream.
  2. An atom is today's stitch record, renamed and made honest. One entry per loop made, or per step that makes none. That keeps chart cells, physics nodes and your saved progress where they are today.
  3. Every atom has a kind, written family.variant: castOn.longTail, increase.m1l, decrease.ssk, marker.place. Each kind is defined once in a registry: what it takes from the needle, what it leaves, how it leans, how it reads from the other side, its chart symbol, its abbreviation and its how-to.
  4. Instructions are spans over atoms. What the knitter reads ("join in the round", "turn and make a double stitch", "divide for the sleeves") is a named span covering one or more atoms. Spans nest: rounds hold instructions, which hold atoms. A span can be marked indivisible, so progress never lands half way through a KFB or a join.
  5. Versions are immutable and named by their content. A project stores a design, a size, a version and an atom index. A new version never moves anyone's knitting. Moving to it is an explicit swap, with "knit up to here" to put progress right. That replaces the current revisions mechanism and needs no migration logic.

What's there today

The code already follows most of this, which is why it's a refactor rather than a rewrite.

  • Written pattern. Each size has sections of RoundSpec: castOn, join, needles, rounds, shaping (with [m1, k8] × 29-style ops), chart, divide, walk, piece, shortRows and bindOff. The samplers generate theirs with the shaping solver. The feline and Paul Klee designs write theirs from tables.
  • Expansion. buildSweater drives the needle machine (knitting/needles.ts), which emits a flat Stitch[]. Each record is a loop of fabric or a step (join, needles, hold, resume, turn, marker), with its yarn slot, piece, wrong-side flag and links to the loops it works. This runs in the browser, which is why the solver's speed reached your phone.
  • Progress is the id of the last record worked: an index into that array. Rounds, labels, charts, the knitting panel's runs and the time log are all derived from it.
  • Revisions can only describe steps added, such as markers, and move progress past them. They can't describe a change to the knitting itself, which is the problem PR #90 ran into.

Three places show where the current record type is strained:

  • Join is a step that quietly rewires the first cast-on's links. The knitter's method (cast on one more, lift the first over it) isn't in the stream at all.
  • KFB is two records, a kfb and an m1 held by the same stitch, which code has to recognise as a pair (makesTwo). That's a composite instruction in disguise.
  • Turn implies the German double stitch ("turn and make a double stitch") without the double stitch being anything you could point at.

The written pattern is worth keeping as a published artifact even though the stream is derived from it. It's the natural source for a "printed pattern" view, and it diffs readably in a pull request: shaping 344 → 360 says more than ten thousand changed atoms. The stream is what's binding: progress, charts and physics all key on it.

Links, meaning which loops each atom works, don't need to be shipped. They follow mechanically from replaying the atoms on a model of the needles, the same machine CI uses. That keeps the file small, but it makes the replay part of the contract, so a test pins it. Each published version records a hash of its replayed links, and the browser checks that hash.

The atom

Definition: an atom is the smallest action on the needles that the rest of the system needs to tell apart. It either makes one loop of fabric, or changes the state of the work without making any.

That's today's granularity, kept deliberately:

  • One chart cell, one fabric atom. A KFB still fills two cells, because it makes two loops.
  • One physics node, one fabric atom, so the settled 3D positions stay keyed exactly as now.
  • Every saved project's progress keeps its meaning, including yours, and so do the time logs.

Each atom kind has a signature, which is all the needle machine needs:

interface Signature {
  /** Live loops it takes, and from where. */
  takes: { from: "needle" | "edge" | "holder" | "otherNeedle"; count: number };
  /** Loops of fabric it makes: 0 for a step, 1 for almost everything else. */
  makes: 0 | 1;
  /** Whether what it makes stays on the needle (a knit) or is finished (a bound-off loop). */
  live: boolean;
  /** For a step: what it does to the needles. */
  effect?: "join" | "turn" | "hold" | "resume" | "changeNeedles" | "placeMarker" | "removeMarker"
         | "newBeginning" | "startPiece" | "makeDouble" | "wrap" | "joinYarn" | "breakYarn";
}

A k2tog takes 2 and makes 1. A make-one takes 0 and makes 1. A bind-off takes 1 and makes 1 that isn't live. A turn takes 0, makes 0 and has the effect "turn". In each case the atom's id is its index in the stream, and the loop it makes, if any, shares that id.

Kinds: families and variants

A kind is family.variant. The family fixes the signature and the role: the needle machine and most code only ever look at the family. The variant carries everything a knitter cares about: how it's worked, how it looks, which way it leans and what it's called. Adding a variant, such as a new cast-on, is a registry entry and nothing else.

Each kind's registry entry:

interface KindDefinition {
  id: string;                     // "decrease.ssk"
  family: Family;                 // fixes the signature and role
  signature: Signature;
  lean?: "left" | "right" | "centre";
  /** The same action from the other side of the work: knit ↔ purl, kfb ↔ pfb, ssk ↔ ssp. */
  fromOtherSide?: string;
  chartSymbol?: ChartSymbol;
  abbreviation: string;           // "ssk", "M1L", "CO"
  label: string;                  // "slip, slip, knit"
  how: string;                    // the sentence the key and the panel show
  steps?: string[];
  /** Hints for things derived from the stream. */
  physics?: { width?: number; rise?: number };
  seconds?: number;               // relative time to work, for estimates
}

A design can still reword any kind for itself, as stitchNotes does today, and can choose variants per context: long-tail at the neck, knitted at the underarm. The variant then lives in the stream, rather than being inferred from where the stitch falls.

Instructions are spans

The stream is flat. Everything a knitter reads is a span: a named range over it, with parameters. Spans nest, and each layer of the screen reads the layer it needs.

interface Span {
  kind: SpanKind;                // "piece" | "section" | "round" | "row" | "instruction" | "repeat" | "chartRow" | "check"
  type?: string;                 // for an instruction: "joinInTheRound", "germanTurn", "divide", "kfb"…
  start: number;                 // first atom
  end: number;                   // one past the last
  params?: Record;   // { holder: "sleeve-right", count: 100 }, { chart: "2015A", row: 19 }
  /** Progress may not stop inside it: a KFB, a join, a turn with its double stitch. */
  indivisible?: boolean;
}

Here are the four places in your sweater where today's records are already composite:

Joining the neck into a round

instruction · joinInTheRound · indivisible
castOn.longTailpassOver.liftOver

Cast on one more and lift the first cast-on stitch over it. That's one extra loop made and one fastened, so the round closes with the count it had. This is your "a knit and a join which subtracts a knit". The links the step rewires today become an ordinary consequence of two atoms.

A German short-row turn at the back of the neck

instruction · germanTurn · indivisible
structure.turnloop.makeDouble

The double stitch becomes an atom that changes a loop, and that loop remembers it's double. A later row knits it as one stitch, and the knitting panel can say exactly that. A wrap and turn would be loop.wrap then structure.turn, and Japanese short rows would be another variant. Short-row methods are variants of a composite instruction, not new families.

Dividing for a sleeve

instruction · divide · { holder: "sleeve-right", hold: 100, castOn: 14 }
holder.hold ×100castOn.knittedcastOn.knitted… ×14

Today one hold step carries a count of 100. As atoms, holding is one step per loop moved, or a single step with a count. Either works. I'd keep a single step with a count, because a knitter doesn't put stitches on hold one at a time. The divide span groups it with the 14 underarm cast-ons, which is the instruction the pattern prints.

Starting a sleeve

instruction · startPiece · { holder: "sleeve-right", pickUpBefore: 7, pickUpAfter: 7 }
holder.resumepickUp ×7work.knit ×100pickUp ×7marker.newBeginning

Repeats are spans too: [m1, k8] × 29 is a repeat span whose children are its 29 passes. The panel can say it as the pattern prints it while progress still moves stitch by stitch. Chart rows are spans that carry the chart id and row, so the chart view never has to rediscover which chart a round came from.

Which side, and what's stored

Store each atom as worked, with the side it's worked from: a purl on a wrong-side row is work.purl on side: "wrong". The stream is a list of things to do, so it should say what to do. How it looks from the right side is a pure function of kind and side, through each kind's fromOtherSide. That's what sides.ts works out today, the other way round.

Per atom, the stream stores the kind, the yarn slot, the side, and the step's parameters where there are any. Pieces, needles, fabric and labels are per span. Colours stay out entirely: a colourway is still a costume.

Measured on your sweater: 121,928 atoms collapse to about 51,000 runs of identical kind and yarn. That's roughly 1 MB of JSON before compression and 10–15 KB gzipped, against the 100–250 KB a size's settled 3D positions already take. Versions are immutable, so old ones stay published for as long as any project might need them, and cost almost nothing to keep.

Versions and progress

  • A project stores { design, size, version, progress }, where progress is an atom index. It always loads the version it was started on, so no later change can move anyone's knitting.
  • Moving to a new version is something the knitter chooses: "this pattern has been updated, switch?" Progress carries across as the same index, and "knit up to here" puts it right where the versions differ. That's exactly your plan for round 55, offered in the app instead of done by hand. The site can show where the versions first differ, from the spans, so the knitter can see whether it's behind or ahead of them.
  • The revisions mechanism goes. Projects saved today all point at "version 1", which is today's build. Its stream is identical to what the browser builds now, so their progress means the same thing.
  • Settled 3D positions are keyed by version, as they're keyed by topology today.

The pipeline in CI

  1. Compile every design and size: source to written pattern to stream, with the stitch-count checks and the knitting rules (floats, colours per round) as today's tests run them.
  2. Freshness check in the pull request's validation: compiled files must match their source, just as settlement-plan --check does for settles. A change to anyone's pattern therefore arrives as a reviewable data diff, summarised by round.
  3. Settle new versions, as the settle workflow already does on main.
  4. Publish: files named by version, plus a manifest of the latest version for each design and size. The deploy picks them up like any other data chunk, under the existing budgets.

The solver's speed then stops mattering to knitters. Solving all 37 pieces with symmetric spacing takes a few minutes, well inside the settle workflow's 90.

Getting there without touching your knit

  1. Compile what exists. Run today's buildSweater in CI, write its Stitch[] as the compiled stream with today's types as kinds, and have the site load it instead of building. A test checks that it's identical to the live build. That makes every existing project, yours included, "version 1" with nothing to migrate.
  2. Spans. Emit rounds, sections, chart rows, repeats and the composite instructions as spans, and move the knitting panel and progress over to them.
  3. Registry. Introduce family.variant kinds and the definitions, at first as a mapping from today's types. Move the key, the panel's words and sides.ts onto it.
  4. Honest atoms. Make join, the double stitch and the KFB pair explicit. This changes the stream, so it's version 2, and existing projects stay on version 1 unless they switch.
  5. Then the shaping change (PR #90's snowflakes and your doubling rule) ships as a new version. You'd swap after round 55 in the app rather than by hand.

PR #90 doesn't have to wait for all of this. Step 1 alone is enough to merge it safely: compile today's patterns as version 1 first, so your project stays on it, then merge #90 as version 2.

Prior art

This environment's network blocks these sites, so this section comes from memory rather than freshly read sources. Treat the details as something to check.

  • Knitout (Carnegie Mellon's Textiles Lab) is a low-level text format for knitting machines. Each line is one operation: knit, tuck, xfer, split, drop, miss, plus yarn-carrier operations like in and out. A versioned header comes first, and higher-level tools compile into it. That's the same split as here between a clever source and a dumb, exact stream, and the same separation of fabric-making operations from operations on the yarn and needles.
  • KnitML was an XML language for hand-knitting patterns. It had elements for knitting and purling, typed increases and decreases, cast-ons with a style attribute, markers and repeats. As I recall, it also kept an authored pattern separate from an expanded, rendered one. That's precedent for families with variants as attributes, and for the written-pattern layer.
  • KnitSpeak, from Stitch Maps, is a parser for written stitch-pattern instructions that produces a drawing of the stitches. That's precedent for treating the written pattern as data rather than prose.
  • The Craft Yarn Council's standard abbreviations are where the families above get their names. M1L and M1R, KFB, K2tog and SSK, SK2P and S2KP, PM, SM and RM, W&T, YO and PU are all there, and they give the registry's abbreviation field a standard to follow.

Decisions for you

How fine an atom?Recommended: today's, one per loop or step, so chart, physics and saved progress line up 1:1. The alternative, one atom per knitter action, makes a KFB one atom with two loops but breaks every index.
Store as worked, or as seen?Recommended: as worked, with a side. The stream is instructions. Appearance is derived.
Ship links, or replay them?Recommended: replay, with a hash to check against. The file stays small, and the replay is the needle machine CI already runs.
Yarn joins and float catchesRecommended: derived for now, as spans the compiler adds where the yarn changes or a float runs long. They become atoms only if the panel needs to stop on them.
Keep the written pattern?Recommended: yes, published beside the stream. It's the readable diff and the source for a printed-pattern view.
Where to start?Recommended: step 1 of the plan (compile today's patterns as version 1), then merge PR #90 as version 2.
